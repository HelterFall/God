# God — автономный исследователь Unity-сборок

God — Android-приложение для глубокого исследования папки Windows-игры на Unity. Его задача — не просто определить версию движка или перечислить DLL, а автоматически восстановить максимально полную техническую картину игры: из каких частей она состоит, как они связаны, какие данные и функции используют и что потребуется реализовать при переносе на другую платформу или в другую среду выполнения.

**Главный результат God — техническое досье по игре и план её переноса.** Документы должны позволять разработчику (в том числе при работе с ИИ-помощником) понять устройство сборки, необходимые подсистемы, зависимости, точки интеграции, порядок реализации и оставшиеся неизвестные без ручной пересылки десятков исходных игровых файлов на анализ.

## Что делает God

Пользователь выбирает корневую папку игры через Android Storage Access Framework (SAF). God самостоятельно выполняет доступные этапы исследования:

1. Обходит папки и составляет инвентаризацию файлов, размеров, типов и доступности.
2. Идентифицирует Unity build: версию, платформу, архитектуру, Mono/IL2CPP и структуру каталогов.
3. Находит контейнеры и вложенные архивы; исследует и извлекает их содержимое там, где формат поддерживается.
4. Анализирует нативные PE-файлы, managed-сборки, metadata, зависимости, импорты, P/Invoke и доступные участки IL.
5. Исследует Unity SerializedFiles, TypeTree, сцены, объекты, компоненты, ссылки и ресурсы.
6. Связывает результаты разных анализаторов: файл → библиотека → тип/метод → вызов/API → компонент сцены → ресурс или platform dependency.
7. Выявляет требования и возможные препятствия при переносе: Windows-only функции, архитектурные ограничения, плагины, графика, ввод, звук, файловая система, потоки и сетевые сервисы.
8. Формирует набор взаимосвязанных документов, граф зависимостей и конкретный план дальнейшей реализации.

Это целевое поведение. Не все перечисленные этапы реализованы в текущей версии; актуальное состояние и ограничения приведены ниже и в аудите.

## Для чего нужен результат

God должен отвечать не только на вопрос «что лежит в папке игры?», но и на вопросы:

- Какую именно версию Unity и какой профиль сборки необходимо учитывать?
- Какие части движка и Unity API реально используются этой игрой?
- Какие игровые сборки, классы, методы и нативные библиотеки связаны друг с другом?
- Какие сцены, GameObject, компоненты и ресурсы связаны между собой?
- Какие файлы загружают или ссылаются на другие файлы?
- Какие функции ожидают Windows, x86/x64 или конкретный native plugin?
- Какие подсистемы целевой среды должны существовать и какие интерфейсы они должны предоставлять?
- Какие связи нужно восстановить между подсистемами, в каком порядке их подключать и как проверить результат?
- Что подтверждено данными, что является предположением, а что пока невозможно определить?

God не должен заставлять пользователя вручную открывать каждый архив, выбирать десятки отдельных файлов и пересылать их ИИ-помощнику по одному. Нормальный сценарий — выбрать папку игры один раз, запустить глубокое исследование и получить проверяемый комплект результатов.

## God и другие проекты

God — самостоятельный инструмент исследования. Он не является runtime, библиотекой или обязательной частью Ramen, RamenUnity либо любого другого проекта.

Исторический опыт работы над Ramen, включая ручное исследование файлов при переносе system-nnn, объясняет, зачем нужен God: автоматизировать повторяющуюся техническую разведку и сократить необходимость ручной передачи игровых файлов на анализ.

RamenUnity — отдельный проект с другой задачей. God не обязан передавать ему отчёты через специальный API или импортёр. Его отчёты предназначены прежде всего для людей и ИИ-помощников, которые используют их как техническую основу разработки. Структурированный JSON нужен для точности, поиска, воспроизводимости и будущей автоматизации, а не ради обязательной межпроектной интеграции.

## Принципы

- **Автономное исследование.** Анализировать выбранную папку целиком, включая вложенные контейнеры поддерживаемых форматов, без обязательной ручной распаковки и подготовки.
- **Связи важнее перечней.** Строить сквозную карту зависимостей и соединений, а не выдавать разрозненные списки файлов и символов.
- **Доказательства вместо догадок.** Для каждого вывода сохранять источник, путь, смещение или идентификатор, способ обнаружения, уверенность и статус декодирования.
- **Полнота с честными границами.** Указывать каждый пропуск, лимит, недоступный файл, неизвестный формат и неразрешённую ссылку.
- **Версионность.** Учитывать различия форматов между версиями Unity и backend Mono/IL2CPP. Не переносить предположения одной версии на другую.
- **Безопасность.** Читать и анализировать файлы, но не запускать игровые EXE/DLL и не исполнять игровой IL. Не изменять оригинальную папку.
- **Ограниченное потребление ресурсов.** Потоковое и позиционное чтение, ограниченная распаковка, отмена и понятные лимиты вместо загрузки всей игры в память.
- **Полезный для разработки результат.** Документы должны объяснять не только находку, но и её значение, зависимые части, необходимые интерфейсы и возможный порядок реализации.

## Целевой комплект отчётов

Итог глубокого анализа — не один гигантский файл, а комплект взаимосвязанных разделов. Названия ниже описывают целевой формат; текущий экспорт ещё не реализует все эти документы.

| Документ | Содержание |
|---|---|
| 00 — GAME OVERVIEW | Краткое резюме, версия Unity, backend, платформа, полнота анализа и главные риски |
| 01 — BUILD PROFILE | Структура сборки, версии, архитектуры, конфигурация и evidence |
| 02 — FILE INVENTORY | Полный список файлов, контейнеров, размеров, типов и статусов чтения |
| 03 — CONTAINERS | Архивы, AssetBundles, UnityFS, вложенность, извлечённые entries и неизвестные содержимые |
| 04 — NATIVE DEPENDENCIES | PE-файлы, архитектуры, импорты/экспорты, DLL, плагины и отсутствующие зависимости |
| 05 — MANAGED CODE | Assemblies, типы, поля, методы, IL, вызовы, P/Invoke и межсборочные связи |
| 06 — UNITY DATA & SCENES | SerializedFiles, TypeTrees, объекты, MonoBehaviour, сцены и ссылки |
| 07 — ASSETS & RESOURCES | Текстуры, меши, материалы, шейдеры, аудио, анимации и внешние данные |
| 08 — DEPENDENCY & WIRING MAP | Граф того, что от чего зависит, кто кого вызывает, что загружает и какие интерфейсы соединяются |
| 09 — PLATFORM REQUIREMENTS | Требования к ОС, CPU/ABI, графике, вводу, звуку, файлам, потокам и сети |
| 10 — PORTING PLAN | Какие подсистемы создать, какие API предоставить, какие связи соединить и в каком порядке |
| 11 — BLOCKERS & UNKNOWNS | Подтверждённые препятствия, потенциальные проблемы, пропуски и проверки, которые ещё нужны |

Для машинной обработки дополнительно предусмотрены структурированные данные, граф связей и manifest с версиями анализатора, покрытием и контрольными суммами. Они дополняют документы, а не заменяют их.

## Что значит «достаточно исследовано»

Досье считается полезным для переноса не потому, что God нашёл много файлов, а когда:

- доступная структура игры инвентаризирована;
- все найденные контейнеры получили явный статус: исследованы, частично исследованы, повреждены, зашифрованы/не поддерживаются или недоступны;
- критические форматы и версии имеют опубликованную матрицу поддержки;
- игровые сборки исследованы настолько глубоко, насколько позволяет поддерживаемый parser;
- связи между кодом, нативными библиотеками, Unity-объектами и ресурсами разрешены или явно помечены как unresolved;
- требования к целевой среде выведены из конкретных evidence, а не из общих предположений;
- карта реализации называет интерфейсы, зависимости и порядок соединения подсистем;
- для каждого неизвестного указано, что именно мешает выводу и какой тест или файл мог бы это разрешить.

Даже полный статический анализ не доказывает динамическое поведение игры. Вызовы через reflection, динамическую загрузку, сетевой контент и некоторые native-механизмы могут потребовать дополнительной проверки. God должен прямо указывать такие случаи, а не придумывать ответ.

## Текущая реализация

Текущий MVP уже умеет:

- Выбирать папку через SAF и обходить её с ограничениями по количеству записей и глубине.
- Находить характерные Unity-файлы и оценивать Mono/IL2CPP по структурным признакам.
- Собирать evidence версии Unity из нескольких источников и не выбирать версию наугад при конфликте.
- Распознавать PE, архитектуры x86/x86-64/ARM64, CLR directory, DLL imports, имена импортируемых функций и ordinal imports из ограниченных PE thunk tables.
- Читать ограниченный набор CLR metadata: Assembly identity, Module, TypeDef, поля, методы, AssemblyRef и распространённые сигнатуры.
- Распознавать SerializedFile и UnityFS, читать ограниченную metadata SerializedFile v19–v26.
- Извлекать ограниченные MonoScript/MonoBehaviour сведения, часть TypeTree и PPtr-ссылок.
- Строить ограниченный локальный граф GameObject–Transform–Component.
- Базовый прогресс обхода папок (путь и счётчик, UI обновляется каждые 128 записей) и запрос отмены анализа.
- Экспортировать Markdown и JSON schemaVersion 24 с начальной ScanCoverage; JSON files[] содержит все entries, а `nativeImportSymbols` — прочитанные DLL/function/ordinal imports в пределах текущих лимитов.
- Публиковать JSON inventory с детерминированным `id`, `parentId`, `identitySource` и `inventoryStatus`. ID строится из хешированного SAF document key, если он есть, иначе — из цепочки родительских ID, относительного пути и порядка одноимённых записей; исходный provider URI в отчёт не попадает.
- Публиковать структурированные ScanIssue в JSON `issues[]` с постоянными кодом, стадией, серьёзностью и путём. Существующий массив `warnings[]` и текст Markdown сохраняют человекочитаемые сообщения; версия JSON остаётся schemaVersion 24.
- Публиковать `scanId` и `analyzerRuns[]`: отдельные записи PE, CLR metadata, Unity header, SerializedFile metadata, локального MonoScript payload и bounded Unity scene graph decoder с ссылкой `inputFileId` на `FileRecord.id`, статусом и причиной. Существующая aggregate `ScanCoverage` остаётся отдельной сводкой.

### Главные ограничения текущего MVP

- UnityFS распознаётся по заголовку, но содержимое и AssetBundle entries пока не распаковываются.
- Полноценная поддержка ZIP и других вложенных контейнеров отсутствует.
- PE-анализ ограничен выборкой файлов и bounded read windows; Import/Thunk tables дают DLL names, имена функций, hints и ordinal imports. Exports, forwarded exports, delay imports и полный граф нативных зависимостей пока не реализованы.
- CLR анализ пока не является полным исследованием IL, P/Invoke и достижимости вызовов.
- IL2CPP metadata parser отсутствует.
- SerializedFile, TypeTree, сцены и объектные payload декодируются ограниченно; текущий граф сцены не гарантированно полный.
- Полноценный декодер основных категорий ресурсов отсутствует.
- Сквозной dependency/wiring graph и porting plan пока не реализованы.
- Отмена на проверяемых границах сохраняет partial report с полным уже собранным inventory; `analyzerRuns[]` сохраняет накопленные результаты PE/CLR, Unity header/SerializedFile, локального MonoScript payload и Unity scene graph, включая queued-записи. Markdown ограничен 20 000 строк. Отчёт помечается `partial=true` и `scanStatus=cancelled`; незавершённые результаты не выдаются за полные.
- Прогресс показывается в основном во время инвентаризации, а не по отдельным стадиям анализаторов.
- Markdown tree ограничен 20 000 строк, тогда как JSON files[] содержит все записи, собранные текущим обходом (до лимита 100 000 entries и глубины 40).
- Потоковой записи больших отчётов пока нет; Markdown/JSON полностью формируются в памяти. Экспорт теперь считает null output stream и ошибки открытия, записи или закрытия ошибкой, а не успешным сохранением.
- `inventoryStatus` показывает только результат обхода папок (`discovered`, `enumerated`, `partial`, `inaccessible`). `analyzerRuns[]` отдельно фиксирует результаты PE, CLR metadata, Unity headers, SerializedFile metadata, локального MonoScript payload и bounded Unity scene graph decoder по каждому применимому файлу (`queued`, `analyzed`, `partial`, `skipped`, `unsupported`, `failed`). Внешний MonoScript payload resolution, external-reference/PPtr resolver stages и остальные analyzer families ещё предстоит подключить к per-file runs. `parentId` связывает дочерние записи с найденной папкой; связи с содержимым контейнеров ещё нет.

Подробная оценка реализации: [технический аудит](docs/AUDIT_2026-11-18.md). Отдельно: [аудит тестирования и CI](docs/TEST_AUDIT_2026-11-19.md).

## Архитектура исходного кода

- MainActivity.kt — Android UI, выбор папки через SAF и экспорт.
- ReportExporter.kt — безопасная запись отчётов в SAF output stream с обработкой ошибок.
- GameScanner.kt — orchestration инвентаризации, эвристик и ограниченных анализаторов без прямой зависимости от Android SAF API.
- ScanFiles.kt — read-only `ScanNode`/`ScanFileAccess` и SAF-адаптеры для `DocumentFile`/`ContentResolver`.
- ScanCoordinator.kt — single-job locking и job-scoped cancellation.
- PartialReportBuilder.kt — partial отчёт с inventory и накопленными analyzer outcomes при отмене.
- ScanCoverage.kt — счётчики покрытия и статусы анализаторов.
- PeParser.kt — ограниченный PE-анализ.
- ClrMetadataParser.kt / ClrSignatureParser.kt — ограниченный CLR metadata и signature analysis.
- UnityFileHeaderParser.kt / UnityMetadataParser.kt — Unity headers и SerializedFile metadata.
- UnityObjectDecoder.kt / UnitySceneGraphResolver.kt — ограниченное декодирование объектов и построение графа сцены.
- UnityExternalPointerResolver.kt / UnityExternalPathResolver.kt / UnityManagedTypeResolver.kt — отдельные шаги разрешения ссылок.

Это текущая реализация, а не окончательная архитектура. По мере развития монолитную orchestration необходимо разделить на файловый слой, inventory, независимые анализаторы, общий граф связей и writer отчётов.

## Использование текущего MVP

1. Установить APK.
2. Выбрать корневую папку распакованной Unity-игры.
3. Запустить анализ.
4. Экспортировать доступный Markdown или JSON-отчёт.

GitHub Actions собирает debug APK при push в main. Открой Actions, выбери успешный запуск Android APK и скачай artifact God-debug-apk.

## Ограничения безопасности и точности

God не запускает EXE/DLL и не исполняет игровой код. Анализ выполняется в пределах поддерживаемых форматов и объявленных лимитов. SAF может не предоставлять доступ ко всем каталогам; большие файлы, неизвестные версии, нестандартные контейнеры и шифрование могут приводить к частичным результатам. Обнаружение признака не равнозначно доказательству фактического runtime-вызова. Если ключ или поддерживаемый способ расшифровки недоступен, содержимое должно быть отмечено как opaque/encrypted, а не объявлено успешно исследованным.
