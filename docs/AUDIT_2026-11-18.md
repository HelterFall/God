## 1. Итог аудита

God уже является не просто поиском файлов: он умеет определять признаки Mono/IL2CPP, извлекать часть PE и CLR metadata, разбирать отдельные Unity SerializedFile и строить ограниченное представление сцены с MonoBehaviour/MonoScript-связями.

При этом God пока **не является полным анализатором игровых сборок**. Самые крупные пробелы — стабильность CI, формальная полнота отчёта, чтение крупных и вложенных контейнеров, IL2CPP metadata, глубокий анализ нативных и managed-зависимостей и расширенное декодирование Unity assets.

Главный принцип развития:

- God только читает и анализирует файлы игры.
- God не запускает EXE/DLL, не исполняет IL, не эмулирует Windows и не рендерит игру.
- RamenUnity отвечает за runtime, исполнение managed-кода, Unity API compatibility и Android backend.
- God передаёт RamenUnity факты, связи, ограничения, предупреждения и оценку совместимости через документированный версионированный формат отчёта.

## 2. Что уже реализовано — не переписывать с нуля

### 2.1. Инвентаризация и идентификация игры

- Выбор каталога через Android Storage Access Framework.
- Рекурсивный обход папки с ограничением количества записей и глубины.
- Поиск характерных Unity-файлов и каталогов.
- Структурная оценка Mono / IL2CPP / смешанной или неопределённой сборки.
- Определение версии Unity по нескольким источникам с сохранением evidence, source и confidence.
- При конфликтующих свидетельствах версия не выбирается наугад.

### 2.2. PE и CLR

- Распознавание PE и архитектур x86, x86-64 и ARM64.
- Определение CLR directory и признака managed assembly.
- Чтение ограниченной CLR metadata: Assembly identity, Module, TypeDef, Field, MethodDef и AssemblyRef.
- Привязка полей и методов к TypeDef через FieldList / MethodList.
- Ограниченный декодер распространённых CLR field/method signatures: примитивы, массивы, указатели, by-ref и generic variables.
- Чтение статической таблицы импортов PE и сводка DLL-зависимостей.

### 2.3. Unity serialized data и сцены

- Распознавание заголовков SerializedFile и UnityFS.
- Ограниченное чтение metadata SerializedFile v19–v26.
- Выборки object records, ClassID, PathID, MonoScript references и external references.
- Ограниченное извлечение TypeTree и базовых идентификаторов сериализованных типов.
- Чтение части MonoScript payload.
- Сопоставление доступных MonoScript с managed TypeDef.
- Разрешение части локальных и внешних PPtr-ссылок.
- Декодирование ограниченных полей GameObject, Transform и MonoBehaviour.
- Построение ограниченного графа GameObject–Transform–Component.
- Неоднозначные и неразрешённые ссылки не должны превращаться в выдуманные совпадения.

### 2.4. Отчёты и тесты

- Экспорт Markdown и JSON.
- JSON содержит schemaVersion 22, версии и evidence Unity, backend assessment, списки сборок, нативные импорты, managed metadata, Type resolutions, Unity metadata, заголовки файлов, files и warnings.
- Есть 11 JVM test-файлов для PE, CLR, MonoScript, Unity headers, metadata, object decoder, scene graph, path/pointer resolution и Unity version resolver.

Для обнаруженных UnityFS и IL2CPP форматов статус явно выставляется unsupported.

### Реализовано в первом срезе

- [x] Счётчики попыток, успешных разборов, ошибок и пропусков PE/CLR/Unity header/SerializedFile metadata.
- [x] Статусы completed / partial / failed / unsupported / not-run / not-applicable.
- [x] Явная отметка UnityFS contents и IL2CPP metadata как unsupported при наличии соответствующих признаков.

### Что ещё нужно добавить

- [ ] Более детальные счётчики read / parsed / partially parsed / skipped / inaccessible / failed по каждому отдельному файлу.
- [x] Первые статусы для измеряемых анализаторов: not-run, completed, partial, unsupported, failed; cancelled пока не сохраняется, так как partial report ещё не реализован.
- [ ] Причину пропуска или частичного результата для каждого затронутого файла.

- [ ] Расширить coverage на scenes, assets, config, PPtr resolution и MonoScript binding; сейчас измеряются PE, CLR metadata, Unity headers, SerializedFile metadata, а UnityFS/IL2CPP явно отмечаются unsupported.
- [ ] Сохранение найденных фактов, если один из последующих анализаторов завершился ошибкой.
- [ ] Частичный отчёт при отмене с пометкой cancelled, а не выдачу такого отчёта за завершённый.

Отсутствие результата не доказывает отсутствие компонента или зависимости в игре. Если God не прочитал файл из-за лимита, отсутствие класса, импорта или объекта в отчёте нельзя трактовать как отсутствие этого элемента в сборке.

**Критерий завершения P1:** каждый вывод можно связать с источником и статусом анализа, а каждый пропуск и лимит видны пользователю и в JSON.

## 5. P1 — стабильный формат отчёта для RamenUnity

Текущий JSON полезен; после добавления scanCoverage его schemaVersion увеличен до 23. Это ещё не заменяет долговременный межпроектный контракт. В репозитории на проверенном commit нет отдельного JSON Schema и manifest-файла отчёта.

### Предлагаемый комплект экспорта

- unity-analysis.json
- unity-analysis.schema.json
- manifest.json

Для очень больших результатов позднее можно добавить:

- files.jsonl
- managed.jsonl
- scenes.jsonl
- assets.jsonl

### Что должен описывать контракт

- [ ] Независимую версию формата, например reportFormatVersion.
- [ ] Версию анализатора God.
- [ ] Время создания отчёта.
- [ ] Идентификатор сборки / fingerprint, не зависящий от локального абсолютного пути пользователя.
- [ ] Unity version, platform, architecture и backend вместе с evidence и confidence.
- [ ] Список анализаторов, версии поддерживаемых ими форматов и их статусы.
- [ ] Сводку scan coverage и применённых лимитов.
- [ ] Managed assemblies, AssemblyRef, types, fields, methods, signatures и P/Invoke по мере реализации.
- [ ] Native binaries, imports, exports и missing dependency candidates по мере реализации.
- [ ] Serialized files, objects, TypeTrees, MonoScripts, PPtr links и scene graph.
- [ ] Warnings, errors, unresolved links и unsupported data.
- [ ] Явное разделение confirmed / inferred / unknown.

### Правила совместимости

- Не переиспользовать номер версии схемы для несовместимых изменений.
- Не удалять неизвестные поля и неизвестные статусы при импорте.
- RamenUnity должен уметь прочитать отчёт более старой версии и безопасно отклонить неподдерживаемую major-версию.
- Отчёт не должен содержать локальные абсолютные пути к личным папкам пользователя.
- Manifest создаётся после всех частей отчёта и содержит их размеры / hashes.
- JSON Schema проверяется в тестах на настоящих sample reports.

**Критерий завершения:** RamenUnity может прочитать sample report, проверить схему, понять частичность анализа и выбрать нужный compatibility profile без ручной обработки текста Markdown.

## 6. P1 — чтение крупных файлов и управление памятью

Подтверждённые текущие ограничения из README и GameScanner:

- До 100 000 записей в дереве.
- Максимальная глубина — 40.
- PE-анализ — до 150 EXE/DLL; первичное чтение до 1 MiB, managed PE при необходимости перечитывается до 4 MiB для CLR metadata.
- Unity header candidates — до 500.
- Для первых 40 Unity metadata candidates читается до 8 MiB; для остальных кандидатов используется ограниченное чтение заголовка.
- Отдельные внешние metadata-файлы тоже ограничены.
- В Markdown-выводе есть предел дерева в 20 000 строк.

Сейчас нет единого файлового API, который предоставлял бы анализаторам декларативные возможности sequential read, positional/random-access read и ограничения SAF provider. PE parser получает byte array, а многие Unity-парсеры работают с ограниченными буферами.

### Что сделать

- [ ] Ввести read-only интерфейс файла с size, sequential stream и доступным по возможности positional read.
- [ ] Явно обозначать SAF provider, который не поддерживает надёжный seek.
- [ ] Не загружать большие файлы полностью в RAM.
- [ ] Читать нужные диапазоны по смещениям, когда формат требует random access.
- [ ] Учитывать 64-битные смещения и проверять переполнения при вычислении диапазонов.
- [ ] Перевести крупные секции отчёта на потоковую запись.
- [ ] Не держать одновременно в памяти Markdown, JSON, все payload и промежуточные копии.
- [ ] Сохранять полный машинный inventory независимо от ограничения текстового дерева.
- [ ] Сделать лимиты настраиваемыми профилями: Quick / Standard / Deep.

**Критерий завершения:** крупная папка игры анализируется с ограниченным потреблением памяти; отчёт показывает всё, что было пропущено или ограничено.

## 12. P2 — Asset Analyzer

- [ ] Mesh: vertex layout, indices, submeshes, bounds.
- [ ] AudioClip: format, channels, frequency, payload references.
- [ ] Material: shader link, properties, textures.
- [ ] Shader: metadata, variants hints, dependencies.
- [ ] AnimationClip и Animator-related structures.
- [ ] Font.

**Критерий завершения:** God выдаёт инвентаризацию ключевых ресурсов и связей, достаточную для понимания состава игры и планирования runtime loaders.

## 14. P3 — Android Compatibility Assessment

Это ключевой мост между God и RamenUnity. Он должен быть evidence-based, а не просто выводить «совместимо / несовместимо».

Каждая находка относится к одной из категорий:

1. **Confirmed blocker** — подтверждённая зависимость или формат, для которого нет Android реализации.
2. **Required implementation** — компонент, который потребуется реализовать в RamenUnity.
3. **Optional integration** — необязательная служба или SDK, которую можно заменить или отключить.
4. **Potential issue** — есть признаки проблемы, но доказательств недостаточно.
5. **Unknown / runtime verification** — статический анализ не может дать ответ.

### Проверяемые категории

- [ ] Native Windows APIs.
- [ ] x86/x64-only native libraries.
- [ ] P/Invoke и отсутствующие DLL.
- [ ] Mono / IL2CPP runtime prerequisites.
- [ ] Unity graphics APIs и render pipeline.
- [ ] Input systems, keyboard, mouse, controller и touch dependencies.
- [ ] Audio backend.
- [ ] Filesystem assumptions.
- [ ] Networking, platform SDKs и optional online integrations.
- [ ] Threading / synchronization primitives.
- [ ] Anti-cheat / DRM indicators — только обнаружение признаков, без попыток обхода.

**Критерий завершения:** RamenUnity получает список конкретных задач с evidence и confidence, а не необоснованную гарантию запуска.

- Отмена использует общий флаг; при очереди заданий поведение нужно сделать отдельным для каждого задания.
- После отмены отчёт не создаётся: это ограничение должно быть заменено partial report.

- Результат Markdown/JSON и состояние анализа не сохраняются как устойчивое состояние при пересоздании Activity.
- UI минимальный, не предоставляет полноценную навигацию по отчёту.

**Критерий завершения:** долгий скан управляем, не дублируется, отменяется предсказуемо и оставляет достоверный частичный результат.

## 19. Критерии «God достаточно зрелый»

God можно считать зрелым анализатором, когда одновременно выполнено следующее:

- [ ] CI стабильно зелёный.
- [ ] Каждое семейство форматов имеет объявленную матрицу поддерживаемых версий.
- [ ] Каждый результат имеет evidence и parser status.
- [ ] Все пропуски и лимиты отражены в coverage.
- [ ] Большие файлы читаются потоково, без необходимости держать их целиком в RAM.
- [ ] Отмена даёт корректный partial report.
- [ ] JSON Schema и manifest валидируются автоматически.
- [ ] RamenUnity может импортировать отчёт, не разбирая Markdown.
- [ ] Mono и IL2CPP анализируются в пределах опубликованной матрицы.
- [ ] UnityFS и основные ресурсы извлекаются в пределах опубликованной матрицы.
- [ ] Сцены и зависимости проверены на реальных сборках нескольких поколений Unity.
- [ ] Compatibility assessment различает blockers, required implementations, optional integrations и unknowns.
- [ ] Приложение корректно работает с большими папками через SAF и не сообщает об успехе при неудачном экспорте.

## 20. Что никогда не должно становиться задачей God

- Запускать EXE/DLL или выполнять игровой IL.
- Подменять Mono runtime или Unity engine.
- Рендерить Unity scenes.
- Реализовывать Android input/audio/graphics runtime.
- Эмулировать Windows.
- Обещать, что статический анализ гарантирует запуск игры.
- Дублировать RamenUnity runtime modules.

Это остаётся ответственностью RamenUnity. God выдаёт проверяемое описание игры и требований к среде выполнения.
