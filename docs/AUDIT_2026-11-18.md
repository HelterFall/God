# God — технический аудит и план достижения целевого результата

**Дата актуализации:** 22 ноября 2026 года  
**Проверенный source-code baseline:** `fc497c90b925bb668bedae08880a0bbb34e04811` (squash merge PR #31).
**Последняя успешная post-merge main проверка:** [run #370](https://github.com/HelterFall/God/actions/runs/44997667707) — 106 JVM tests, debug APK build и artifact upload завершились успешно на этом commit.
**Назначение:** зафиксировать реальный уровень реализации God относительно миссии автономного исследования Unity-сборки и подготовки Porting Dossier.

> Это технический снимок. Утверждения о текущем коде относятся к проверенному source commit. Документы актуализируются отдельно; успешный CI не означает, что все анализаторы реализованы.

## 1. Итог аудита

God уже вышел за рамки простого поиска Unity-файлов. В нём есть обход выбранной папки, эвристики Mono/IL2CPP, multi-source Unity version evidence, PE/CLR metadata readers и ограниченный анализ SerializedFile, MonoScript, object payload и scene graph.

Но God **пока не выполняет основную конечную задачу**. Он не исследует все вложенные контейнеры, не строит полный граф связей кода и ресурсов, не декодирует значительную часть Unity assets, не анализирует IL2CPP metadata и не составляет доказательный план переноса с wiring map.

Правильная продуктовая цель:

- выбрать корневую папку игры один раз;
- автоматически исследовать доступные файлы и поддерживаемые вложенные контейнеры;
- связать файловые, native, managed, Unity object и asset уровни;
- выявить требования игры к Unity и платформенным функциям;
- выдать навигационное досье с evidence, dependency graph, конкретными задачами переноса и неизвестными.

God — самостоятельный read-only исследовательский инструмент. Работа в прежнем проекте Ramen, включая перенос system-nnn, объясняет мотивацию автоматизации. RamenUnity — отдельный проект, и не должен рассматриваться как обязательный runtime-потребитель отчётов God. Никакой обязательный импортёр, API contract или runtime coupling между проектами не нужен.

## 2. Проверенный baseline

### Реализовано в коде на проверенном source commit

- SAF folder picker и ограниченная рекурсивная инвентаризация.
- Поиск характерных Unity build files.
- Структурная оценка Mono/IL2CPP и сбор evidence версии Unity.
- PE recognition и архитектуры x86/x86-64/ARM64; ARM64 synthetic PE32+ fixture проверяется тестом.
- Определение CLR directory и ограниченное чтение CLR metadata.
- Assembly identity, Module, TypeDef, поля, методы, AssemblyRef и базовые field/method signatures.
- Static PE imports: bounded section/RVA и PE32/PE32+ thunk parsing; извлекаются DLL names, named functions с Hint и ordinal imports. `nativeImportSymbols` попадает в JSON, imported symbols — в Markdown; пути покрыты synthetic parser/scanner tests.
- Unity SerializedFile header recognition, включая современные v22+ layout.
- UnityFS signature/header recognition без чтения содержимого.
- SerializedFile metadata v19–v26 в bounded окне.
- Object record samples, ClassID counts, MonoScript references и external-file paths.
- Ограниченный TypeTree summary и отдельные полные деревья для выбранных типов.
- Локальный MonoScript payload decoding и часть MonoScript → managed TypeDef resolution.
- Ограниченный GameObject/Transform/MonoBehaviour decoding.
- Ограниченный локальный GameObject–Transform–Component scene graph; сам resolver сцены разрешает только локальные PPtr (fileID=0), до 128 GameObjects на файл.
- Отдельные bounded resolvers исследуют часть внешних PPtr и MonoScript references, но не объединяют их в полный межфайловый scene graph.
- Markdown/JSON export: JSON schemaVersion 24; top-level `scanId` и `analyzerRuns[]` содержат per-file outcomes для PE, CLR metadata, Unity headers и SerializedFile metadata с `inputFileId` → `FileRecord.id`, status/reason; существующие `files[]`, `ScanCoverage`, `warnings[]` и schemaVersion 24 сохранены.
- ScanCoverage для inventory и статусов отдельных analyzer families.
- `FileRecord` для inventory: стабильный SHA-256 ID, parentId, источник identity и отдельный `inventoryStatus`; SAF provider key хешируется и не публикуется, partial report сохраняет файловую иерархию. `AnalyzerRun` с scan-scoped ID связывает PE/CLR/Unity header/SerializedFile outcomes с тем же FileRecord; resolver stages и остальные analyzer families пока используют aggregate ScanCoverage без отдельных per-file runs.
- Структурированные `ScanIssue` для текущих диагностик inventory, PE, CLR, Unity и отмены: JSON `issues[]` содержит code/stage/severity/path/message, а legacy `warnings[]` и Markdown сохраняют человекочитаемый текст. Это начальный диагностический слой, а не полная система per-file findings/evidence.
- Базовый progress callback, job-scoped cancellation и partial report с полным inventory; если отмена наступила после старта PE/CLR/Unity header/SerializedFile stages, отчёт сохраняет уже выполненные и queued AnalyzerRun records, созданные к моменту отмены.
- JSON inventory сохраняет все собранные entries в пределах текущих лимитов; Markdown tree независимо ограничен 20 000 строк.

### Структура кода

В приложении есть отдельные парсеры/resolvers для PE, CLR metadata/signatures, Unity headers/metadata, object decoding, scene graph, MonoScript/type resolution и ScanCoverage. Центральная orchestration и формирование отчётов всё ещё сосредоточены в GameScanner.kt. Базовые `ScanNode`/`ScanFileAccess` и SAF-адаптер уже отделяют `GameScanner` от Android API, но полноценные positional FileAccess, graph store и analyzer pipeline пока не реализованы.

### Правило интерпретации

Если parser просмотрел только sample, отсутствие объекта или зависимости в sample не доказывает отсутствие этой сущности в игре. В отчёте должны сохраняться candidate count, attempted count, skipped count, parsed/partial/failed status и применённые limits.

## 4. ScanCoverage — важная основа, но пока не полная система покрытия

Текущая реализация различает aggregate ScanCoverage для analyzer families и per-file AnalyzerRun для PE/CLR/Unity header/SerializedFile. Они не заменяют друг друга. На проверенном PR #31 head отражены:

- inventory discovered entries/files/directories/bytes, inaccessible directories, depth and entry cap;
- PE candidates, attempted, parsed, failed and skipped;
- CLR metadata candidates and bounded parse outcomes;
- Unity file-header candidates and outcomes;
- SerializedFile metadata candidates and outcomes;
- UnityFS content status as unsupported when UnityFS headers are found;
- IL2CPP metadata status as unsupported when structural evidence is found.

Статусы включают not-applicable, not-run, completed, partial, failed и unsupported. Это уже помогает отличать «ничего не найдено» от «анализатор не смог проверить».

### Что ещё нужно

- [x] Per-file status с причиной для PE, CLR metadata, Unity header и SerializedFile metadata через `analyzerRuns[]`; остаются resolver stages и другие analyzer families.
- [ ] Раздельно учитывать inaccessible, permission denied, not seekable, too large, truncated, unsupported, corrupted и encrypted/opaque.
- [x] Связывать PE/CLR/Unity header/SerializedFile analyzer attempts с конкретными `FileRecord.id`; добавить такие связи для resolver stages и остальных analyzer families.
- [ ] Указывать версию парсера и поддерживаемый format/version range.
- [ ] Отражать пропуски вложенных контейнеров и их дочерних entries.
- [x] Создавать явно помеченный partial report при отмене: сохранять inventory и уже созданные completed/partial/failed/skipped/queued AnalyzerRun records для пройденных PE/CLR/Unity header/SerializedFile этапов.
- [ ] Не считать общий scan completed, если обнаружены неподдерживаемые или не запущенные требуемые анализаторы.

**Критерий:** по любому объекту инвентаризации можно понять, был ли он исследован, каким способом, насколько глубоко и почему результат ограничен.

## 14. P3 — Dependency/wiring graph

Это главная связующая функция, которая превращает результаты отдельных parser'ов в понимание игры.

### Nodes

Files, containers, PE/native binaries, managed assemblies, types, methods, fields, scenes, objects, components, MonoScripts, assets, Unity APIs, platform APIs, runtime subsystems, implementation tasks and blockers.

### Edges

Contains, extracted-from, imports, exports, references, inherits, implements, calls-static, calls-possibly-dynamic, P/Invoke, loads-library, attaches-script, component-of, PPtr, loads-asset, uses-Unity-API, requires-platform-API, depends-on-subsystem and unresolved.

### Правила

- Каждая связь обязана ссылаться на evidence и иметь confidence.
- Неоднозначное совпадение имён не становится confirmed edge.
- Static call-site не считается runtime execution.
- AssemblyRef не считается доказательством использования каждого типа.
- У каждого unresolved edge есть причина.
- Новые анализаторы сразу добавляют nodes/edges в общую модель.

**Критерий:** можно пройти от porting requirement к нужным игровым методам/объектам и исходным файлам, а затем увидеть связанные зависимости.

## 15. P3 — Porting assessment and implementation plan

God должен объяснять, что потребуется разработать в целевой среде, а не ограничиваться выводом «несовместимо с Android».

Каждая задача должна включать:

- Required subsystem/interface.
- Какая функция игры её требует.
- Evidence: file, type, method, IL offset, import, object ID, asset или config value.
- Входы/выходы и dependencies.
- Кто вызывает этот интерфейс и какие компоненты используют его результат.
- Возможные реализации/замены и их ограничения.
- Порядок реализации, bootstrap/load order.
- Validation test.
- Неизвестные и уровень уверенности.

### Классификация находок

- Confirmed fact.
- Strong evidence.
- Inference.
- Confirmed blocker.
- Required implementation.
- Optional integration.
- Potential issue.
- Unknown / runtime verification.

**Критерий:** Porting Dossier даёт практический список подсистем, связей, порядка реализации и тестов с трассировкой до исходных evidence. Он не гарантирует, что статический анализ полностью предскажет runtime-поведение.

## 18. Определение зрелости God

God считается зрелым для конкретного Unity/build profile, если:

- все доступные файлы инвентаризированы;
- все поддерживаемые контейнеры исследованы до согласованной глубины;
- каждый analyzer отчитался о статусе и coverage;
- code/data/native/asset layers связаны общим графом;
- критические Unity/Mono/IL2CPP formats имеют проверенные fixtures;
- важные платформенные требования подтверждены evidence;
- Porting Dossier называет необходимые подсистемы, контракты, связи, порядок и проверки;
- все unknowns и blockers перечислены без сокрытия;
- отчёт воспроизводим и навигационен.

Это не означает «God полностью декодирует любой файл любой игры». Это означает, что по указанному профилю его поддержка измерена, документирована и полезна для реальной работы. Test coverage и проблемы качества зафиксированы отдельно: [TEST_AUDIT_2026-11-19.md](TEST_AUDIT_2026-11-19.md).

## 19. Что God не должен делать

- Запускать игровые EXE/DLL или исполнять игровой IL.
- Подменять Unity runtime, Mono или IL2CPP executor.
- Рендерить игровые сцены.
- Реализовывать graphics/input/audio runtime целевой платформы.
- Эмулировать Windows.
- Делать вид, что неизвестный/encrypted/corrupt контент успешно декодирован.
- Гарантировать запуск игры по одному статическому отчёту.
- Требовать обязательного API или импорта отчётов в Ramen/RamenUnity.
